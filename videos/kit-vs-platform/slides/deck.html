03 · Vì sao không tự viết harness
Tốc độ · Phép thử mất giá

Phần tự viết harness mất giá; phần nội bộ thì không

Tốc độ
Vendor và open source ra feature theo tháng

Subagent, skill, hook, sandbox, chạy headless, SDK. Harness tự viết phải đuổi theo mãi — mỗi lần đuổi là công sức không tạo ra khác biệt.

Phép thử mất giá

“Nếu quý sau vendor ra đúng feature này, khoản đầu tư của mình có mất trắng không?”

✗ Mất

Agent orchestration layer, chat UI

✓ Không mất

Code graph hệ thống nội bộ, template theo chuẩn tài liệu của tổ chức, checklist review, connector tới tool nội bộ — vì bên ngoài không có

03 · Vì sao không tự viết harness
L3 và L4

Automation level là tính chất của workflow, không phải của tool

Cùng một harness, hai workflow khác nhau:

L3
bước 1→hỏi người→bước 2→hỏi người→bước 3→hỏi người

Cho dừng hỏi người ở mỗi bước.

L4
skill→skill→skill→draft→approval gate

Cho chạy trọn một chuỗi skill rồi trình draft ở approval gate cuối.

04 · Bảng so sánh so sai đối tượng
1 / 2

Bảng so sánh đang so hai cách triển khai, không so harness với platform

Nó đặt harness dùng tương tác trong IDE cạnh một platform chạy trên server. So harness chạy headless kèm kit với platform tự viết thì từng dòng đổi như sau:

Dòng trong bảngThực tế
L3 so với L4Automation level do workflow quyết định. Kit tài liệu hiện chủ động dừng để hỏi người (L3) vì đó là design choice, không phải do harness giới hạn.
Tool cá nhân so với cloudHarness chạy được trên server: Claude Code có chế độ non-interactive, Agent SDK và tích hợp GitHub Actions; Kiro CLI có --no-interactive, đã chạy thử thực tế.
Task rời so với end-to-end“Một lệnh giao trọn feature” là một skill chain workflow, tức phần kit. Kit hiện đã có lệnh slash cho từng loại tài liệu.
04 · Bảng so sánh so sai đối tượng
2 / 2

Multi-repo là bài toán dữ liệu; chỉ audit tập trung là khoảng trống thật

Dòng trong bảngThực tế
Single repo so với multi-repoĐây là vấn đề dữ liệu. Code graph nhiều repo phơi ra qua CLI hoặc MCP thì harness nào cũng dùng được. Dòng này ủng hộ đề xuất, không bác nó.
Không có gate, không có auditHuman gate đã có: PR review, branch protection, hook của harness. Audit tập trung là khoảng trống thật (Kiro lưu session log local trên máy từng người), lấp bằng một layer mỏng: LLM gateway, telemetry, thu log về một chỗ.
Không tích hợp tool chuyên sâuNối tool qua CLI hoặc MCP chính là connector trong kit. CLI cho Jira và Confluence đã chứng minh cách này khi MCP chưa được bật.

“Trợ lý cá nhân” so với “dây chuyền sản xuất” không đứng vững: cùng một harness có thể là cả hai, tuỳ nó chạy ở đâu và chạy workflow nào.

09 · Bước tiếp theo
Trước khi trình

Bốn bằng chứng cần có trước khi trình

1
Chạy trên một hệ thống có sẵn

Chuỗi basic design → detail design → unit test của team dự án; ghi thời gian và số lỗi review so với làm tay.

2
Chạy headless một lần

Cùng chuỗi đó, có approval gate cuối — chứng minh mức L4 không cần harness tự viết.

3
Chạy trên hai harness

Cùng một kit; ghi phần phải sửa ở adapter.

4
Dựng thử LLM gateway

Ghi cost và log theo user — đủ để trả lời câu hỏi governance.
